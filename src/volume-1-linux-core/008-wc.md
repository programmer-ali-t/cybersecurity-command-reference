## FUNCTION

**Purpose.** Count lines, words, bytes, or characters in files or standard input.

**Formal definition.** `wc` streams input and counts: `-l` newline characters, `-w` whitespace-separated tokens, `-c` bytes, `-m` characters (multibyte-aware), `-L` longest line length. It reads the entire input — never seek-based.

**When to use.**

- Verify file size by lines.
- Compare record counts before/after processing.
- Assert in scripts.

**When NOT to use.**

- Counting matches — use `grep -c`.
- Unique counts — use `sort -u | wc -l` or `uniq`.

**Preferred alternatives.**

| Situation | Better tool |
|---|---|
| Count non-empty lines | `grep -c .` |
| Distinct count | `sort -u \| wc -l` |
| Pattern count | `grep -c PATTERN` |

## APPLICATION

**Minimal example.**

```bash
wc -l access.log
```

**Realistic example — multibyte-aware count.**

```bash
wc -lm report.txt
```

**Expected output.**

```text
  1234   5678  91234 report.txt
```

The three numbers are `lines`, `words`, `bytes` when `-l -w -c` are used together (the default). With `-l -m`, the third column is characters.

**Interpretation.**

- Line count = newline count. A file with no trailing newline reports N lines even though a human sees N+1.
- `-c` vs `-m` differ on UTF-8.
- Multiple files produce a `total` line at the end.
- `-L` reports the length of the longest line, which on binary input can be misleading.

**Common misreadings.**

| Misreading | Reality |
|---|---|
| `wc -l` counts logical lines | It counts `\n` characters |
| `-c` is size on disk | It is byte count, not block count |
| `-w` uses spaces | It uses any whitespace (space, tab, newline) |
| `wc` is O(1) on large files | It reads the whole file; never seeks |

## OPERATIONAL

**Privilege required.** None.

**Failure modes.**

| Failure | Cause | Fix |
|---|---|---|
| Slow on multi-GB file | Full read required | Expected; use `stat -c %s` for byte size only |
| Total line missing with one file | No total for single input | Expected |
| Wrong count after `dos2unix` skipped | CRLF treated as content | Normalize line endings first |

**Blast radius.** None.

**Recovery path.** Not applicable.

**Performance impact.** Reads full file. ~500 MB/s on SSD. On NFS, throughput dominates.

## EDUCATIONAL

**Learning objective.** Explain the difference between `-c` and `-m` on UTF-8, and why `wc -l` counts newlines not lines.

**Prerequisites.** Understanding of UTF-8 encoding, basic byte vs. character concept.

**Guided exercise (10 min).**

Create a file containing the word "hello" followed by a newline. Run `wc -c` and `wc -m`. Explain the result. Then add an Arabic word and repeat.

**Challenge (30 min).**

Create a file without a trailing newline. Assert `wc -l` equals what you expect. Explain the off-by-one. Write a script that always reports the correct human line count.

**Quiz.**

1. Why does `wc -l` on a file without trailing newline report one fewer line?
2. When does `-c` differ from `-m`?
3. What does `-L` measure?
4. Why is `wc` not suitable for very large files when only size is needed?

**Real-world story.**

A pipeline asserted "100 lines" but received 99 because the file lacked a trailing newline. The failing assertion was traced to `wc -l` semantics, not data loss. Lesson: document your newline conventions.
